# Job Email Tracker（求职邮件追踪）

**把招聘邮件变成一张可以放心照着做的日程。** 它读投递回执、测评邀请、面试通知和拒信，判断每一封「是什么事」「什么时候」「哪个时区」，排进看板。拿不准的时候，它会直说，而不是猜一个。

**在线演示：** https://job-command-center-eta-two.vercel.app
（演示里的公司和邮件全部是虚构的，所有解析都在浏览器里完成。）

[English](./README.md)

## 为什么做这个

秋招期间每周几十封邮件，中英文混着，跨四个时区。代价最高的错误很具体：

- 把**固定场次**当成截止时间 → 错过考试
- 把**截止时间**当成固定场次 → 白等一场不存在的考试
- 时间显示成**错的时区** → 差 12 个小时
- 把「邀请于 09:09 生效」当成考试时间 → 邮件一到，看板就显示「已逾期」

直接让大模型「把时间抽出来」，这四种错它都会犯，而且很自信。所以目标不是「抽得越多越好」，而是**绝不显示一个错的时间**。

## 核心设计：模型只摘抄，规则做决定

模型只允许从原文里**逐字摘出片段**：公司名、岗位、说时间的那句话、地点、对事件类型的建议。它不输出日期，不输出时区，不做任何决定。

会伤到用户的判断全部交给确定性规则：是场次还是截止、哪个时区、是不是同一件事、够不够把握排进日程。规则可以逐条读、逐条测、逐条改。

由此得到两条性质：

1. **模型只有否决权，没有提名权。** 模型和规则对「这是什么事」看法不同时，这件事进「待确认」。模型能把一件事拦在日程外面，但不能把任何一件事送进日程。
2. **每个结论都能解释。** 每张卡片的详情里有高亮的原文片段，以及每一步判断的依据。

## 真实邮件上的结果

在我自己的 147 封招聘邮件上测得（流程邮件 92 封、岗位广告 50 封、无关 5 封）。方法和注意事项见 [docs/EVALUATION.md](./docs/EVALUATION.md)。

| | 只用规则 | 规则+模型（首次） | 规则+模型（修复后） |
|---|---|---|---|
| **精确率**：进日程的条目完全正确的比例（目标 > 95%） | 73.8% | 75.0% | **98.5%** |
| **召回率**：流程邮件完全正确且进了日程的比例（目标 > 70%） | 33.7% | 55.4% | **72.8%** |
| 广告/无关邮件错上日程（共 55 封） | 3 | 8 | 1 |
| 公司名正确（共 92 封） | 59.8% | 98.9% | 98.9% |

**需要说明：**「修复后」一列是在同一批 147 封邮件上测的，而修复正是对着这批邮件做的，所以这个数字偏乐观。还没有在一批没见过的新邮件上验证过。「首次」一列才是没有被污染的数字。

```
engine/   解析引擎。纯 TypeScript，零运行时依赖，461 个测试
web/      Next.js 应用（即演示站）。引擎以拷贝方式放在 web/lib/tracker-core，359 个测试

```

## 运行

需要 Node.js 20.9 或更高版本。

```bash
cd engine && npm ci && npm test
cd web && npm ci && npm run dev      # http://localhost:3000
```

## 已知局限

- 尚未在没见过的新邮件上验证。
- 没有后端：演示里的手动操作存在浏览器本地。接入真实邮箱、把状态存到服务端是下一步。
- 评测集里仍有一封宣讲会广告会被排进日程（信里确实写了现场面试的时间）。
- 没有任何时区线索的邮件按设计进「待确认」，即使人能从公司猜出时区。

## 不在这个仓库里的东西

真实邮件、人工真值、以及回放真实邮件的回归测试都留在私有环境。这个仓库只有代码、合成数据和汇总后的评测数字。
